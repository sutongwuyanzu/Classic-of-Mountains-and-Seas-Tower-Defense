本文是后续实施计划，不是已完成证明。本次仅创建本文件，未实现计划中的功能。

## 0. 2026-09-19 范围更新

用户决定先打磨游戏本体，Steam 工作进入冻结状态。保留已完成的 Windows 构建、存档可靠性、素材台账和本地 SteamPipe 模板，但不继续进行 Steamworks SDK、Cloud、后台、商店、上传、送审或发售工作。

恢复 Steam 工作的前提是游戏本体完成新的实际游玩验收：首局理解、战斗信息可读性、核心策略、性能和稳定性均有可复现证据。此更新优先于本文原有的 S05-S11 执行顺序。

## 1. 目标与范围

用户已决定暂停微信小程序/小游戏方向，优先推进 Steam 上架。保留现有 `wechatgame/`、`miniprogram/` 和资源；微信账号注册、广告、真机调试不再作为桌面工作的前置条件。

建议首发定位：山海经题材、随机召灵与羁绊组合、自由布阵的单人离线塔防。首先交付 Windows x64 键鼠版本，完整支持已有五关及已实现的重复游玩模式。

建议商业方案：付费买断完整版，是否增加免费 Demo 另行决定。此为建议，不代表用户已批准价格、Demo 范围或任何商店承诺；所有不依赖该选择的技术工作可先执行。

首发建议承诺：

- Windows 11 x64 首先实测，其他 Windows 版本通过测试后再列入系统要求。
- 简体中文完整可玩；是否首发英文在商店素材制作前确认。
- 完整离线战斗与本地存档、明确的波次检查点恢复规则。
- 鼠标操作完整，补齐暂停、取消、窗口模式等必要键盘操作。
- 保留当前美术风格和玩法数值，以稳定性、可读性和发行完整性为主。

首发不自动扩张：原生 3D 重制、更换引擎、联机、排行榜服务、DLC、内购、手柄全流程、Steam Deck 认证、macOS/Linux 原生包。手柄和云存档可以增加，但一旦在商店承诺就必须实测兑现。

## 3. Steam 发布条件与排期约束

按 2026-09-18 查阅的 Valve 官方资料：

- Steamworks 提供个人持有内容时的入驻填写方式；用户本人处理真实身份、收款和税务信息。Steam 的入驻方式并不替代所在地的经营与税务义务。[入驻说明](https://partner.steamgames.com/doc/gettingstarted/onboarding)
- 每款应用 Steam Direct 费用为 100 美元或等值本币，可能另计适用税费；达到官方规定的 1,000 美元调整后总收入门槛后可在结算中收回，不是无条件退费。[费用说明](https://partner.steamgames.com/doc/gettingstarted/appfee)
- 发布日同时受付款后 30 天等待期、Coming Soon 公开至少两周、商店和游戏审核等条件约束。两段等待可重叠，不简单相加。[入驻说明](https://partner.steamgames.com/doc/gettingstarted/onboarding)、[发布流程](https://partner.steamgames.com/doc/store/releasing)
- 商店资料先送审，再提交游戏构建审核；资料审核通常需 3～5 个工作日，官方建议至少提前 7 天提交并留修订时间。[发布流程](https://partner.steamgames.com/doc/store/releasing)
- Steamworks API 集成不是上架强制条件。成就、云存档和手柄不能作为无条件阻断本地发行包的前置任务。[API 概览](https://partner.steamgames.com/doc/sdk/api)
- 当前项目使用 AI 美术，应在内容调查中如实说明预生成的玩家可见内容；若无运行时 AI，不能把预生成资源误填成运行时生成。[内容调查](https://partner.steamgames.com/doc/gettingstarted/contentsurvey)

最早可发布日应取“费用等待期结束、Coming Soon 满两周、审核通过、版本验收完成”中的最晚日期，尚未取得账号资料时不承诺具体发售日。

本计划默认国际 Steam。若改为蒸汽平台或其他地区发行路径，需另行核对相应条件。

### S01：Windows 发行构建

主要文件：`package.json`、`package-lock.json`、`electron-builder.yml`、`scripts/build-portable.ps1`、`steam/README.md`。

- 先比较现有两条构建路线，选一条可复现的正式 Windows x64 目录产物；另一条保留明确的本地调试定位，避免产物悄悄不一致。
- 正式 Steam depot 包含 EXE、Electron 运行库、资源和所需许可证；Steam 客户端直接启动游戏 EXE。NSIS 只作为站外安装包，可延期。
- 保留 Electron 隔离设置。核对锁定依赖、支持状态、漏洞是否可达；需要升级时单独做兼容性回归，不顺手全量升级。
- 统一发行版本、构建号、EXE 名称与元信息。独立目录写构建清单，包含源码提交、dirty 状态、依赖版本、文件 SHA-256；未提交包不得冒充干净提交产物。
- 素材按运行时引用纳入；剔除源图、提示词、录屏、测试日志、个人存档、内部账号文件和测试 AppID。不得凭文件名认定资源无用后删除源码资产。
- 构建输出用唯一版本目录；如脚本必须递归删除旧输出，先验证绝对路径确在指定 release/dist 下，仅处理明确授权的可再生产物。
- 核对应用图标各尺寸和授权。构建完成必须从产物目录启动，不能仅跑 `npm run steam`。

验收：无 Node/Python 开发环境的 Windows 标准用户可运行；中文/空格路径与不同工作目录可启动；断网资源完整；目标目录无源图、密钥和测试存档；构建失败退出码非零。新工具和缓存放 `G:\Codex files`，项目依赖沿用仓库已有布局。

### S02：存档、退出与异常可靠性

主要文件：`electron/main.cjs`、`electron/preload.cjs`、`src/main.js` 的存档和生命周期部分；必要时增加职责清晰的小型存档模块。

- 确认实际 `app.getPath('userData')`，冻结发布身份和路径策略；更换产品名或打包方式必须验证旧档迁移，不让老用户看见空白进度。
- 明确唯一权威存档与迁移规则。现有逻辑比较浏览器存储和文件时间戳，接云存档前必须防止本机旧 localStorage 把 Steam 同步下来的有效进度覆盖。
- 审查当前 `tmp -> 备份 -> 删除原文件 -> rename` 的中断窗口，模拟失败后再选择最小安全写入修复。只保证 JSON 可解析不等于存档结构有效，按版本和真实字段校验。
- 写入失败保留旧文件、备份和本局结果；缺盘空间、无写权限、损坏主档、损坏备份都能说明状态，不靠吞异常“通过”。
- 双启动只保留一个可写实例或证明不会竞争写档；关闭窗口前的待写入处理与超时必须有明确策略。
- 保持波次检查点语义。抽卡待领取、转运签弹窗、进化选择、Boss 死亡等边界不能因重开或退出重复发奖、重复扣款或留下跨局计时器。
- 收敛本地错误日志：捕捉主进程、preload 和 renderer 的故障，包含版本与阶段，限制大小；避免断开的 stdout/stderr 导致 EPIPE 二次崩溃，不记录凭证或完整用户存档。
- 不再假定历史 EPIPE 一定来自游戏：先区分外部测试脚本与正式包，复现后再修。

验收：旧版本升级到候选包后进度保留；检查点可继续；强制结束后至少恢复最近成功写入的有效档；失败结算仍可返回或重开；快速连点重开无旧弹窗串局。故障注入只用隔离测试目录，不碰真实玩家存档。

### S03：桌面设置和键鼠交互

主要文件：`index.html`、`styles.css`、`src/main.js`、Electron 窗口接口。

- 增加清晰的窗口化/无边框全屏、音量、画面反馈强度入口；优先复用现有音频设置。窗口全屏与网页 DOM 全屏需协调，避免退出后 UI 尺寸错误。
- Esc 按状态优先处理取消拖放/目标选择、关闭最上层弹窗、暂停；待领取召灵结果关闭后仍可继续领取，不能丢失已付款结果。
- 若增加暂停/倍速/召灵快捷键，复用既有按钮动作及其禁用规则；弹窗、文本输入和按键重复不应触发多次付费。
- 不让窗口尺寸记忆把窗口恢复到已断开的显示器外。图形选项属于设备设置，不随未来云存档覆盖另一台电脑的屏幕配置。
- 检查 1280×720、1366×768、1920×1080、2560×1440、超宽屏，及 100%/125%/150%/200% DPI；关键数字、升级/召灵/暂停按钮不得裁切或遮挡。

验收：选关至重开全链路可用；Alt-Tab、最小化、休眠恢复、全屏切换反复操作均可继续；单独留存 720p 与高 DPI 截图。手柄不是本批范围，不宣传支持。

### S04：游戏内容与首局验收

主要文件：先只读 `src/main.js`、`shared/game-core.js` 与资源；明确缺陷的修复再局部编辑。

- 由至少 3 名不了解项目的玩家做首局测试，记录首次召灵、首次部署、理解目标、首次失败及重开用时。目标：多数人在 30 秒内理解守护封印、召灵和部署，不需要开发者口头解释。
- 五关标准难度实际打完；低/高难度覆盖关键波次，第四、五关实测两路分配。Boss 胜负判定、免疫提示、技能目标、合成和必选妖灵评分需覆盖。
- 建立固定种子/初始存档测试用例，记录胜负、资源、召灵次数、升级次数、路段漏怪与耗时；自动模拟用于定位，不能替代真实操作和视觉验收。
- 对比新存档和高成长存档，识别成长是否掩盖不合理难度；保留实际完成时长，禁止凭“五关×15波”宣传游玩小时数。
- 检查无尽和每日试炼的已实现行为；离线本地日期种子不宣传成服务器公平竞赛，也不新增排行榜需求。
- 数值调整必须先提交证据、影响范围与建议；用户确认后逐项试测，不以移植 Steam 为由重做抽卡池、成长或经济。
- 使用实机截图按敌我辨识、立绘完整、命中来源、技能范围、首领突出程度列视觉缺陷；每批只修确认项，避免全套素材重生。

验收：已知阻断性玩法缺陷清零；每关有实测记录；至少两种有意义阵容思路的可行性经过玩家测试；用户认可首局与代表性后期战斗片段。若没人参加试玩，状态写“待玩家验收”。

### S05：性能与资源预算

- 选定并记录 CPU、GPU、内存、系统、驱动、分辨率、构建号；实际测完再写 Steam 最低配置。
- 场景：选关冷启动、首次召灵、大量妖灵、双路首领、无尽高压、最高倍速、连续 20 次重开、持续 60 分钟。
- 测量帧时间分位数、加载时间、进程内存、资源解码、长帧与输入迟滞。区分前台和后台；30/60/144 Hz 下核对游戏时间与波次推进，不能把卡顿带来的慢动作算稳定。
- 初始工程目标：参考机 1080p 60 FPS，p95 帧间隔不高于 20 ms、p99 不高于 33 ms；冷启动至可操作不超过 8 秒。作为待基线校准的目标，不是假称已达标或 Valve 规则。
- 若声明低配模式，低配参考机至少 30 FPS，并确认玩法计时无误。60 分钟与重复重开不得持续无界增长；先测量再确定内存硬预算。
- 本地资源约 310.5 MiB，不预设它全是运行时负担。分析源图、屏幕实际尺寸和解码成本，使用可见差异对比后再改格式或尺寸。

验收：提交 `steam/PERFORMANCE.md`；每次优化保留前后同场景数据，不仅记录平均 FPS；实际更改不得影响随机结果、伤害或放置判定。

### S06：Steam 平台适配与成就

本项推荐但可协商延期。若延期，保留本地勋章且商店不声明 Steam 成就。

- 用 0.5～1 天技术验证选兼容现有 Electron/Node ABI 的维护中绑定；先核对来源、许可证、预编译 Windows x64 支持和打包原生模块要求，不提前指定未经验证的库。
- 原生平台调用只放主进程，preload 暴露最小白名单接口；renderer 不获得任意文件或平台调用能力。
- 区分“桌面版”“Steam 已初始化”“当前账号可用”三个状态。现有 `isSteam()` 只识别桌面 bridge，不适合当 SDK 登录状态。
- 将 `Core.MEDALS` 的稳定 ID 映射到 Steam 后台成就；本地解锁、待同步、平台确认分开，离线后联网可补同步，重复调用幂等。
- 覆盖客户端未启动、当前账号无授权、初始化失败、正常退出、Overlay 打开/关闭、Steam 离线模式。Overlay 与 blur 的暂停状态不能互相覆盖导致无法继续。
- 开发测试 AppID 与正式配置分开；正式产物不包含 `steam_appid.txt` 测试文件，不将 AppID 误当密码。登录凭据和上传令牌才属于敏感资料。

验收：真实目标 AppID 的 Steam 客户端中取得用户身份、触发一个成就、重启保留、离线再联网补发均有证据。mock 和 SpaceWar 测试不能替代目标游戏验收。SDK 调试失败不应破坏独立桌面构建。

### S07：Steam Cloud

优先评估 Auto-Cloud，只有确有选择性同步需求才用 Cloud API；官方提供两种机制。[Steam Cloud 文档](https://partner.steamgames.com/doc/features/cloud)

- 依赖 S02 的稳定保存协议及账号识别方案。Auto-Cloud 不替游戏解决本地账号串档，不能把通用 `userData` 全目录当云存档。
- 选定账号隔离路径，迁移旧本地档时由当前用户明确选择归属；禁止把旧档自动导入每个登录过的 Steam 账号。
- 只同步必要进度文件；不上传 Chromium 缓存、日志、GPU 配置、临时写入文件或设备专属设置。固定文件清单与大小额度。
- 用户显式选择的 Steam 云冲突结果应被游戏尊重；不再用残留 localStorage 时间戳反向覆盖。是否云同步本地备份文件在方案中写清。
- 有效性与版本迁移先于加载；未来版本存档不静默降级覆盖，失败时保留数据并给出恢复路径。

验收：同一账号 A 机存档、退出同步、B 机下载继续；离线分叉后按用户选择恢复；同电脑 Steam 账号 A/B 不串档；重装恢复有效；失败不清空本地档。暂无双机或账号时标记未验收，不显示完成。

### S08：素材来源、AI 披露与许可

输出：`steam/ASSET_PROVENANCE.csv`、第三方说明、内容调查草稿。

- 逐类记录妖灵、敌人、背景、特效、字体、音效、音乐、图标的文件路径、来源、生成工具或作者、许可依据、是否修改、需要署名项。
- 用户做过 MakePlay 项目不自动证明平台素材的再发行权。核对实际使用内容；不明资源先记录并隔离于发行清单，用户核实或选择有许可素材替代。
- 保留 AI 素材提示词和源图的本地证据，发行包只装运行时素材；不把“AI 生成”当作不需要审查内容来源的理由。
- 内容调查按最终游戏实际可见素材填写，核对是否存在联网生成；由用户审核后提交，不隐藏 AI 美术使用。[内容调查说明](https://partner.steamgames.com/doc/gettingstarted/contentsurvey)
- 打包保留 Electron/Chromium、字体和其他库要求的许可证/声明；不要因为源码在 GitHub 公开就擅自给整个仓库套用开源许可证。

验收：每类实际发行资源均能追溯；无法确认的项明确阻断相关资源发布；已有来源充分的资源不要求无意义重制。

### S09：商店页与宣传材料

输出建议位于 `steam/store/`，内部资料不能含个人信息。草稿完成并通过用户审核后才上传。

- 文案包含短介绍、核心循环、五关与组合策略、已验收模式、语言、输入方式、最低/推荐配置、支持联系方式。仅写成品已实现且可玩的功能。
- 至少 5 张真实游戏截图，目标 1920×1080 或以上，覆盖第一关清晰布阵、羁绊组合、双路、首领、后期阵容；截图不以概念图或假 HUD 代替。[商店图像规范](https://partner.steamgames.com/doc/store/assets/standard)
- 胶囊图按当前官方尺寸制作：Header 920×430、Small 462×174、Main 1232×706、Vertical 748×896；制作前再核对后台模板。另补齐后台要求的库图、Logo 和图标，不凭旧博客尺寸制作。[商店图像规范](https://partner.steamgames.com/doc/store/assets/standard)
- 建议 45～75 秒实机预告：开场展示玩法，随后召灵、布阵、羁绊、双路与首领，不以长 Logo 片头或未入游戏的 AI 影片代替实机。
- 买断定价根据真实内容时长、重玩价值及同类商品调查另行建议；不擅自设置价格或首发折扣。
- 明确公开 GitHub/完整网页与买断版本的关系。保留现状直到用户决定，不能擅自关闭 Pages、改私有仓库或削减网页版关卡。
- Steam 商店公开和上市后支持由用户拥有明确联系方式；避免承诺无人维护的路线图。

验收：每条商店功能声明能指向 QA 项；宣传截图与最终候选包一致；文字可读、无版本号占位和未实现标签；正式名称与用户选择一致。

### S10：SteamPipe 与候选版本

主要文件：后续新增 `steam/build/*.vdf` 模板、构建检查脚本、QA 文档；SDK/SteamCMD 等工具放 `G:\Codex files\Steamworks`。

- 缺 AppID/DepotID 时生成带显式占位符的模板，并让校验在占位符存在时失败，禁止猜 ID 上传。
- `ContentRoot` 指向 S01 的已验收目录，`BuildOutput` 在发行内容目录之外；文件映射白名单，无凭据、测试数据、源图和下载缓存。[SteamPipe 文档](https://partner.steamgames.com/doc/sdk/uploading)
- 稳定 EXE 名称和启动项，Windows x64 depot/包授权配置核对；用户明确授权上传后仅上传指定私有测试分支，默认不设 `SetLive` 自动发布到 default。
- 从 Steam 客户端实际安装、启动、更新、校验文件、卸载重装；测试中文用户名、非系统盘 Steam 库、标准权限和离线启动。
- S06/S07 若纳入首发，必须随同真正的 Steam 下载安装包验收。把 EXE 添加为“非 Steam 游戏”不算 SteamPipe/身份/云存档测试。
- 创建候选版本清单：源码提交、构建号、Steam BuildID、DepotID、EXE 名称、资源哈希、测试机器、已知问题、上一可用 BuildID。
- `deploy-pages.yml` 目前发布根目录：建议后续建立网页产物白名单，避免将内部 Steam 发布文档与打包资料直接发布到 Pages。公开 Git 仓库本身也不能放敏感内容。

验收：测试账号从私有分支下载成功；从上一包升级保留档；Steam 显示运行与退出正常；回退构建时不盲目覆盖更高版本存档。

### S11：送审、发售与后续维护

- 商店页与构建检查表分别整理；先准备完整可审材料，用户批准后再送审。商店审核通过后公开 Coming Soon，并记录实际开始日期。[发布流程](https://partner.steamgames.com/doc/store/releasing)
- 原先私有分支通过验收的候选包，在用户授权下设置到审核要求的分支/配置；不是私测通过就直接公开售卖。
- 所有承诺的首发功能实际通过，完成等待期和审核；用户确认价格、日期、地区、展示能力与已知问题后才执行 Release App。
- 发售后复核购买/安装/启动路径、旧档、成就和云存档（如承诺），保留上一可用包和可恢复测试档。
- 故障分级：启动失败、数据丢失、付款后无法游玩优先；视觉小问题进入补丁。收集日志前提供本地导出，未经同意不后台上传个人信息。
- 热修复制原复现场景与邻近功能验证；版本回退遵守存档兼容范围，不默认旧包一定能读新档。

## 8. Terra 工作规则与交付格式

- 每批先核对仓库、分支、HEAD 和未提交修改，按 S00→S01→S02 顺序开始；同文件操作顺序执行，素材来源盘点与用户试玩可并行。
- 不覆盖他人改动。不得删除微信工程；共享逻辑的必要改动仍须保持现有共享测试通过，不趁机新增微信功能。
- 计划阶段不动玩法；后续只能在工作包范围实施，确认的数值或商业取舍再执行。
- 不自动提交、推送、上传、送审或发售；此前某次 push 的授权不等于永久发布授权。没有账号凭据也可产出模板和本地候选包。
- 每批执行针对性验证、`npm run check`、`git diff --check`；Electron/打包改动验证实际产物，UI 改动必须留实际截图。
- 跨存档、平台和打包的复杂批次完成后，用独立只读 Agent 对抗审查，再验证确认的问题。不可用时明确记录“仅自查”，不能冒称独立审查。
- 不为跑绿结构断言而删掉有价值测试；随着新增桌面风险补充行为测试，不批量重写既有战斗系统。
- 每批记录：编号、基线、修改文件、复现/目标、结果、验证证据、剩余问题、下一编号。证据必须标明测试版本和机器。
- 一个工作包完成后继续下一个不受阻工作包；只在可验收批次、真实阻断或产品决定时汇报。不能承诺计算机关闭或无可用任务环境时仍持续运行。
- 排期、性能数字、规则建议均可按证据修订，修订要记原因；禁止把计划中的验收标准直接标成通过。
